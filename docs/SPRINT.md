# Seven-day MVP sprint

Scope: Android, online-only, synthetic demo account, exactly one elbow flexion/extension exercise. The demonstration workflow is sign in -> assignment -> tracked exercise -> complete-cycle count -> stop/save -> server history. Thresholds, target and instructions are demonstration defaults requiring professional review before patient use. Camera frames and landmarks remain on-device; only session summaries leave the phone.

Developer A leads Flutter; Developer B leads FastAPI/PostgreSQL/Railway. Each reviews the other's PRs, including paired contract work. Assume eight working hours per developer each day: five implementation hours, two protected integration/device-testing hours, and one review/documentation hour. Protect the last three hours; move incomplete features into the next day instead of borrowing that time. Day 6 implementation time is regression work; Day 7 is freeze and rehearsal. Day numbers are relative to the agreed sprint start, not calendar promises.

## Day 2 phone gate

A leads and B witnesses. Record device model, Android version, SDK/plugin versions, commit, lighting, camera position, measured frame rate/processing latency and date. Implement permission handling, camera image conversion/rotation, preview, confidence-filtered shoulder/elbow/wrist angle, lifecycle disposal and recovery. Do not upload images or landmarks.

Engineering acceptance defaults for this gate (also require review): ten deliberate extended -> flexed -> extended cycles count ten; holding near either threshold does not create counts; occluding a required joint at any phase and reappearing flexed cannot complete a partial rep; interruptions and pause/resume require a fresh full cycle. Observe tracking responsiveness for two minutes on the actual phone (initial engineering target >=10 processed samples/second, no overlap/backlog, no thermal crash). Capture observations without recording patient imagery. Decide go/no-go together and document shortcomings; a simulated pass does not pass this gate. Professional review of movement instructions and thresholds remains separate from engineering acceptance.

## Acceptance and deferred scope

- Online sign-in using a seeded synthetic account; incorrect/expired credentials have a clear next action.
- Authenticated assignment is exactly the pre-created demo exercise; no account ID is supplied for ownership.
- Start/stop/tracking states are visible. Complete cycles count once; jitter, missing joints and time gaps cannot complete partial cycles.
- Stop freezes timestamps/count/mode/reason/UUID. Failed save remains in memory on the open screen; Retry save resends the same summary. Restarting the app loses unsaved data by design.
- Identical retries return one record, conflicting UUID reuse returns a conflict, and user B cannot read/save against user A's assignment or obtain user A's history.
- Server history reflects saved sessions. Loading, empty, validation, authentication, network and server states are understandable.
- CI checks pass in both repos; contract snapshot/example match; compatible backend deploys before client release.

Deferred: offline access, local session databases, durable retry/upload queues, background synchronization, doctor/guardian portals, voice commands, chatbot, payments, notifications, additional exercises, iOS and web. Do not add them to recover lost sprint time.
